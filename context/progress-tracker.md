## Resolved Decisions

- **Authorized sources (V1):** YouTube + YouTube Music domains only. Concrete allow-list enforced in Unit 4 before any yt-dlp call.
- **Target platform (V1):** Android only — builds and testing via Expo Go on an Android device/emulator. iOS functional but out of scope for V1.
- **File retention (V1):** fixed TTL of 24 hours for `server/temp/` and `server/output/` files; cleanup routine built in Unit 8.
- **Version restructure (Unit 20 re-plan):** V2 absorbs the former V3 ("Expanded separation") scope; the former V4 becomes V3. New division: V2 = Units 16–26, V3 = Units 27–33. The former V2 + V3 end-to-end verifications merge into Unit 26.
- **4-stem separation is the standard (V2):** `separate.py --stems 4` (vocals, drums, bass, other) is the default for current-app jobs; `stems: 2` (with `instrumental`) is retained only for V1-era API/payload compat.
- **Editing window / stem mixer moves into V2 core flow:** the Result screen on a 4-stem job is the editing window — per-stem sliders (0–100%) → custom mixed stems, live client-side preview, and async mix-render export via FFmpeg gain sums (Unit 23).
- **Mix renders are their own job records (Unit 23):** `POST /api/jobs/:jobId/mix` creates a separate job (`parentJobId` links it to the source job; `mixOptions` persisted so a redelivered render rebuilds from state) walking `queued → mixing → encoding → completed/failed`, and writes `mix.<ext>` into the parent's `output/` dir under the same ≤24 h TTL. `GET /api/jobs/:parentId` keeps its byte-identical shape (Invariant 8).
- **Batches are a view, not a store (Unit 24):** a batch = a shared internal `JobRecord.batchId` UUID; batch endpoints scan `stemora:job:*` and group — no new Redis structures. `POST /api/batch` validates every URL before creating anything, then rolls back best-effort on mid-way persist/enqueue failure.
- **Cancel is cooperative + flag-based, not process-killing (Unit 24):** cancel sets `stemora:cancel:<jobId>` (TTL = file TTL) and flips the record to `cancelled` at tap time (fast poller feedback); the separation worker checks the flag at stage boundaries, runs `finishCancelled` (clean dirs, resolve), so no subprocess is ever killed mid-stage — a finishing stage runs out. Idempotent; queued BullMQ jobs also get a best-effort `remove()`. `cancelled` is a terminal `JobStatus` value but cancelled jobs are never written to on-device history.
- **Editing-window preview is client-side (Unit 23):** four simultaneous `expo-audio` players with per-player `volume` driven by the sliders; a server-rendered preview clip stays the documented fallback until a Unit 26 on-device sync test says otherwise.
- **Faster separation (V2):** a `quality: fast` mode (fewer Demucs shifts / reduced overlap) targeting ~2× lower CPU time; measured, not guessed, in the Unit 20 spec. **Measured result (Unit 20):** the ~2× target is NOT reachable with demucs 4.1.0 CPU models — `fast` = `overlap 0.0` (shifts 0) delivers **~21% lower wall-clock** vs `standard` (`overlap 0.25`, shifts 0) on this 4-core Windows CPU (4-stem CLI apples-to-apples: 112.6s vs 142.8s on the 19s "Me at the zoo" clip; in-process isolated: 81.7s vs 103.8s). `torch threads=4` gave no gain; `mdx_extra`/`mdx_extra_q` both slower; `split=False` crashes htdemucs on long inputs; legacy `demucs` absent from the 4.1.0 registry.
- **Waveform data is derived in the pipeline, not rendered on demand (Unit 25):** Invariant 1 forbids FFmpeg in HTTP handlers, so per-stem waveform peaks are computed in the **encode pipeline stage** — FFmpeg decodes each stem WAV to mono f32 at 44.1 kHz, buckets max-abs amplitude into `WAVEFORM_BUCKETS = 200` values in `[0,1]` (3-decimal rounded), cached as `output/<jobId>/<stem>.peaks.json` under the same ≤24 h TTL. The additive read-only `GET /api/jobs/:jobId/waveform/:stem` endpoint serves the cache (404 `JOB_NOT_FOUND`/`FILE_NOT_FOUND`, no new error codes); a missing/corrupt peaks file degrades the app to the existing scrubber — waveform failure is never a job failure. Pre-Unit-25 jobs simply have no `peaks.json` (degradation path covers them). Loop interaction: A/B handles always rendered once duration is known; dragging a handle re-shapes the region and auto-enables looping; the `Repeat` toggle flips looping; wrap = a 250 ms interval polling `player.currentTime` and seeking to region start past region end — `expo-audio`'s `loop` property (whole-file only) and `useAudioSampleListener` (needs RECORD_AUDIO) were both rejected in the spec.

## Architecture Decisions

- No general-purpose database in V1/V2; job state is an in-memory `Map` (V1) then a Redis-backed BullMQ queue (V2). Revisit only when V3's shared hosting/production load justifies object storage + auth (see `architecture.md`).
- Two-language backend is deliberate: Node.js owns orchestration/HTTP, Python owns AI inference only, invoked as a subprocess.
- V1 targets zero hosting cost — everything runs on local/dev hardware.
- Editing-window mix renders are async jobs (Node `mixer` service, FFmpeg gain sums) sharing the queue — never inline renders in an HTTP handler (Invariant 1).
